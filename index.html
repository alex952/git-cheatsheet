Conflictos de Merge: qué son y cómo resolverlos

Un conflicto aparece cuando Git no puede decidir solo qué versión conservar: ambas ramas modificaron las mismas líneas (o una borró un archivo que la otra editó).

Cómo se ve un conflicto

Git marca el archivo con tres separadores. Todo lo que está entre ellos es tu decisión:

function saludar() {
<<<<<<< HEAD
  return "Hola, mundo";
=======
  return "Hello, world";
>>>>>>> feature/ingles
}

Cómo leerlo

  • Entre <<<<<<< y =======: tu versión (la rama en la que estás, "ours").
  • Entre ======= y >>>>>>>: la versión entrante (la rama que fusionas, "theirs").
  • Tu trabajo: dejar el código final correcto y borrar los tres marcadores.
  • Con merge.conflictStyle zdiff3 aparece además la versión del ancestro común (|||||||), muy útil para entender qué cambió cada lado.

El proceso paso a paso

Detectagit merge feature falla con "CONFLICT". Git queda a medias.
Localizagit status lista los archivos en "both modified" (unmerged).
EditaAbre cada archivo, decide el contenido final y quita los marcadores.
Marcagit add archivo le dice a Git que ese archivo ya está resuelto.
Terminagit commit (o git merge --continue) crea el commit de fusión.

Estrategias para resolverlos

    


      

        
✍️ 1. Manual (la más común)

        

          
git status

          
Ver qué archivos están en conflicto ("Unmerged paths").

        

        

          
git diff --name-only --diff-filter=U

          
Lista solo los archivos sin resolver.

        

        

          
git add <archivo>

          
Marca el archivo como resuelto tras editarlo. Esencial

        

        

          
git merge --continue

          
Cierra el merge cuando no quedan conflictos (equivale a git commit).

        

      


      

        
🎯 2. Quedarte con un lado (por archivo)

        

          
git checkout --ours -- <archivo>

          
Descarta la versión entrante y deja la tuya. También: git restore --ours.

        

        

          
git checkout --theirs -- <archivo>

          
Descarta la tuya y deja la entrante. Después hay que hacer git add.

        

        
Ojo en un rebase: ours y theirs se invierten. Durante git rebase main, "ours" es main (sobre lo que reaplicas) y "theirs" son tus commits.

      


      

        
⚡ 3. Resolver automáticamente al fusionar

        

          
git merge -X ours feature

          
Fusiona todo, pero en las líneas en conflicto gana tu versión. Lo no conflictivo de la otra rama sí entra.

        

        

          
git merge -X theirs feature

          
Igual, pero en los conflictos gana la rama entrante.

        

        

          
git merge -s ours feature

          
Registra el merge pero ignora por completo el contenido de feature. Peligroso

        

      


      

        
🧰 4. Herramientas visuales

        

          
git mergetool

          
Abre tu herramienta de merge (VS Code, Meld, vimdiff…) archivo por archivo.

        

        

          
git config --global merge.tool vscode

          
Configura qué herramienta usa mergetool.

        

        

          
git config --global merge.conflictStyle zdiff3

          
Muestra también el ancestro común dentro del conflicto. Recomendado

        

        

          
git diff --ours

          
Compara el archivo en conflicto contra tu versión (también --theirs y --base).

        

      


      

        
🚪 5. Abortar y volver al inicio

        

          
git merge --abort

          
Cancela el merge y deja todo como estaba antes. Seguro

        

        

          
git rebase --abort

          
Cancela un rebase en curso y restaura la rama original.

        

        

          
git cherry-pick --abort

          
Cancela un cherry-pick conflictivo.

        

        

          
git checkout -m <archivo>

          
Recrea los marcadores de conflicto de un archivo que ya habías "resuelto" mal (antes de commitear).

        

      


      

        
🔁 6. Conflictos durante un rebase

        

          
git rebase --continue

          
Tras resolver y hacer git add, sigue con el siguiente commit. Puedes tener que resolver varias veces (una por commit).

        

        

          
git rebase --skip

          
Descarta el commit actual que provoca el conflicto. Pierde ese commit

        

        

          
git cherry-pick --continue

          
Igual que arriba para un cherry-pick (y git stash pop: resuelve, git add y borra el stash con git stash drop).

        

      


      

        
🧠 7. Que Git recuerde tus resoluciones

        

          
git config --global rerere.enabled true

          
"Reuse recorded resolution": si vuelves a ver el mismo conflicto (típico al rebasar muchas veces), Git aplica tu resolución anterior solo.

        

        

          
git rerere status

          
Muestra qué archivos tienen resolución registrada.

        

      


      

        
🛡️ 8. Cómo evitarlos

        
    
          
  • Integra main en tu rama con frecuencia (git pull --rebase o git merge main).
    • 
          
  • Ramas pequeñas y de vida corta.
    • 
          
  • Evita reformatear archivos enteros en el mismo PR que cambias lógica.
    • 
          
  • Comunícate: dos personas tocando el mismo archivo = conflicto asegurado.
    • 
          
  • Tras resolver, compila y pasa los tests: un conflicto "resuelto" puede compilar mal aunque Git no se queje.
    • 
        

      

    

  


  
  

    

      
Git Worktrees: varias ramas abiertas a la vez

      
Un worktree es un directorio de trabajo adicional enlazado al mismo repositorio. Cada uno tiene su propia rama activa, pero todos comparten el historial y los objetos.


      

        

          
📁 mi-proyecto/

          main
          
Worktree principal. Contiene la carpeta .git/ real.

        

        

          
📁 ../mi-proyecto-hotfix/

          hotfix/bug-123
          
Un parche urgente sin tocar tu trabajo a medias.

        

        

          
📁 ../mi-proyecto-review/

          feature/login
          
Para revisar la rama de otra persona en paralelo.

        

        
🗄️ Un único repositorio compartido: commits, ramas, tags y remotos viven en mi-proyecto/.git

      


      

        

          
¿Para qué sirve?

          
    
            
  • Te llega un bug urgente y no quieres hacer stash ni un commit "WIP".
    • 
            
  • Revisar un PR ejecutándolo en local sin cambiar tu rama.
    • 
            
  • Lanzar tests o builds largos en una rama mientras sigues programando en otra.
    • 
            
  • Comparar el comportamiento de dos versiones lado a lado.
    • 
            
  • Trabajar con agentes/asistentes de IA en paralelo, cada uno en su rama aislada.
    • 
          

        

        

          
Frente a las alternativas

          
    
            
  • vs. git stash: no hay que guardar/restaurar nada; ambos estados coexisten.
    • 
            
  • vs. clonar de nuevo: no duplicas el historial ni los objetos, y los commits se ven al instante en todos los worktrees.
    • 
            
  • vs. git switch: cambiar de rama reescribe archivos y invalida caches/builds; con worktrees cada carpeta conserva los suyos.
    • 
          

        

      


      
Regla de oro: una misma rama no puede estar activa en dos worktrees a la vez. Git lo impide para que no pises tus propios cambios.

    


    

      
Escenario típico: bug urgente

      
Estás en feature/pagos con cambios sin terminar y llega un hotfix:


# 1. Crea un worktree nuevo con una rama nueva basada en main
git worktree add -b hotfix/bug-123 ../mi-proyecto-hotfix main

# 2. Trabaja ahí sin tocar tu carpeta original
cd ../mi-proyecto-hotfix
git commit -am "Arregla el bug 123"
git push -u origin hotfix/bug-123

# 3. Cuando se haya fusionado, vuelve y limpia
cd ../mi-proyecto
git worktree remove ../mi-proyecto-hotfix
git branch -d hotfix/bug-123

    


    

      

        
🌳 Comandos de worktree

        

          
git worktree add <ruta> <rama>

          
Crea un worktree con una rama existente. Esencial

        

        

          
git worktree add -b <nueva> <ruta> <base>

          
Crea la rama nueva a partir de <base> y su worktree a la vez.

        

        

          
git worktree add --detach <ruta> <tag-o-commit>

          
Worktree en HEAD desatachado, ideal para inspeccionar un tag o commit sin crear rama.

        

        

          
git worktree list

          
Muestra todos los worktrees, su commit y su rama.

        

      


      

        
🧹 Mantenimiento

        

          
git worktree remove <ruta>

          
Borra el worktree (falla si tiene cambios sin commitear; usa --force para forzar).

        

        

          
git worktree prune

          
Limpia referencias de worktrees cuya carpeta borraste a mano.

        

        

          
git worktree move <ruta> <nueva-ruta>

          
Mueve un worktree (no uses mv a secas).

        

        

          
git worktree lock <ruta>

          
Evita que prune lo elimine (útil en discos externos o unidades de red). Se revierte con unlock.

        

      


      

        
💡 Consejos y trampas

        
    
          
  • Crea los worktrees fuera de la carpeta del proyecto (../nombre) para no anidarlos.
    • 
          
  • Cada worktree necesita sus propias dependencias (node_modules, venv…) y su .env, porque están ignorados por Git.
    • 
          
  • Los stash, ramas y tags son compartidos: un commit hecho en un worktree aparece al instante en los demás.
    • 
          
  • Borrar la carpeta a mano deja metadatos huérfanos: usa remove o prune.
    • 
          
  • Los submódulos tienen soporte limitado en worktrees; compruébalo antes si los usas.
    • 
        

      

    

  


  
  

    

      
GitHub: lo que Git no te cuenta

      
Git es la herramienta local de control de versiones; GitHub es la plataforma que aloja repositorios remotos y añade colaboración: Pull Requests, Issues, Actions, permisos y más.


      
Ciclo de vida de un Pull Request

      

        
Ramagit switch -c feature/x desde un main actualizado.

        
CommitsTrabaja y haz commits pequeños con mensajes claros.

        
Pushgit push -u origin feature/x sube la rama a GitHub.

        
Abre el PRDescribe el cambio, enlaza el Issue y pide revisores.

        
Revisión + CIComentarios, cambios solicitados y checks de Actions en verde.

        
MergeSe fusiona con el método elegido y se borra la rama.

      


      
Los 3 métodos de merge de un PR

      
El botón verde de GitHub ofrece tres formas de integrar el mismo PR. Las diferencias están en cómo queda el historial de main (los círculos punteados son commits que ya no llegan a main tal cual):

      

        

          
Create a merge commit

          

          
Conserva todos los commits y añade un commit de fusión. Historial fiel pero con mucho ruido.

        

        

          
Squash and merge

          

          
Aplasta todo el PR en un único commit. Historial limpio y 1 PR = 1 commit. El más usado.

        

        

          
Rebase and merge

          

          
Reaplica cada commit sobre main (con hashes nuevos). Historial lineal sin commit de fusión.

        

      

    


    

      

        
🔑 Remotos y autenticación

        

          
git remote -v

          
Lista los remotos configurados y sus URLs.

        

        

          
git remote add origin git@github.com:usuario/repo.git

          
Conecta tu repo local con uno de GitHub (SSH).

Genera una clave SSH; sube la pública (.pub) en Settings → SSH and GPG keys.

        

        

          
ssh -T git@github.com

          
Comprueba que GitHub reconoce tu clave.

        

        

          
gh auth login

          
Inicia sesión con la CLI oficial gh (navegador o token). Esencial

        

      


      

        
🔀 Pull Requests con gh

        

          
gh pr create --fill

          
Abre un PR rellenando título y cuerpo con tus commits. Añade --draft para un borrador. Esencial

        

        

          
gh pr list

          
Lista los PRs abiertos del repo.

        

        

          
gh pr checkout 123

          
Descarga y cambia a la rama del PR #123 para probarlo en local.

        

        

          
gh pr checks

          
Estado de los checks de CI del PR actual.

        

        

          
gh pr review 123 --approve

          
Aprueba un PR (o --request-changes / --comment con -b "texto").

        

        

          
gh pr merge --squash --delete-branch

          
Fusiona con squash y borra la rama (alternativas: --merge, --rebase).

        

      


      

        
🍴 Forks y contribuir a proyectos ajenos

        

          
gh repo fork --clone

          
Crea tu fork en GitHub, lo clona y configura upstream automáticamente.

        

        

          
git remote add upstream <url-del-original>

          
Añade el repo original como remoto upstream (si no usaste gh).

        

        

          
git fetch upstream

          
Trae las novedades del proyecto original.

        

        

          
git rebase upstream/main

          
Actualiza tu rama con el original (o git merge upstream/main) y luego git push a tu fork.

        

        

          
gh repo sync

          
Sincroniza tu fork con el original en un solo comando.

        

      


      

        
🐛 Issues y Actions

        

          
gh issue create

          
Crea un Issue desde la terminal (gh issue list para verlos).

        

        

          
gh run list

          
Últimas ejecuciones de GitHub Actions.

        

        

          
gh run watch

          
Sigue en vivo una ejecución en curso.

        

        

          
gh run view --log-failed

          
Muestra solo los logs de los pasos que fallaron.

        

        
En la descripción de un PR, Closes #42 (también Fixes / Resolves) cierra el Issue #42 automáticamente al fusionar.

      


      

        
🛡️ Protección de ramas y calidad

        
    
          
  • Branch protection / Rulesets (Settings → Rules): exigir PR, número mínimo de aprobaciones, checks verdes y bloquear force-push sobre main.
    • 
          
  • CODEOWNERS (.github/CODEOWNERS): asigna revisores automáticamente según la ruta modificada.
    • 
          
  • Plantilla de PR (.github/pull_request_template.md): estructura la descripción de cada PR.
    • 
          
  • Merge queue: encola PRs y los valida contra el estado más reciente de main.
    • 
          
  • Dependabot: abre PRs automáticos para actualizar dependencias vulnerables.
    • 
        

      


      

        
⚙️ GitHub Actions: un CI mínimo

        
Archivo .github/workflows/ci.yml:


name: CI
on:
  pull_request:
  push:
    branches: [main]
jobs:
  test:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - run: npm ci
      - run: npm test

        
Hospedar esta misma página: Settings → Pages → rama main / carpeta raíz.

      

    

  


  
  

    

      
Estrategias de ramas más comunes

      
No hay una estrategia "correcta": depende de cómo despliega tu equipo. Cada fila del gráfico es una rama; el tiempo avanza hacia la derecha. Las etiquetas amarillas son tags/releases y las líneas que cambian de fila son ramificaciones o merges.

1. GitHub Flow

      
Una sola rama estable (main) que siempre es desplegable. Todo cambio entra por una rama corta y un Pull Request.

      

      

        

          
Flujo

          
    
            
  • Crea una rama descriptiva desde main.
    • 
            
  • Haz commits y súbela pronto; abre el PR (incluso en borrador).
    • 
            
  • Revisión + CI en verde.
    • 
            
  • Merge a main y despliegue inmediato.
    • 
          

          
ProsSimple, rápido, fácil de aprender.

          
ContrasNo gestiona varias versiones en producción a la vez.

        

        

          
Comandos típicos


git switch -c feature/login main
git push -u origin feature/login
# PR → revisión → merge en GitHub
git switch main && git pull
git branch -d feature/login

        

      

    


    

      
2. Git Flow

      
Modelo clásico con dos ramas permanentes y tres tipos de ramas de apoyo. Pensado para software con versiones numeradas.

      

      

        

          
Flujo

          
    
            
  • main: solo código publicado, cada commit lleva un tag de versión.
    • 
            
  • develop: rama de integración con lo próximo a salir.
    • 
            
  • feature/*: salen de develop y vuelven a develop.
    • 
            
  • release/*: congelan develop para estabilizar; al terminar se fusionan a main (con tag) y a develop.
    • 
            
  • hotfix/*: salen de main para urgencias; se fusionan a main y a develop.
    • 
          

          
ProsOrdena releases y soporta mantenimiento de versiones.

          
ContrasMuchas ramas, merges frecuentes, poco apto para despliegue continuo.

        

        

          
Comandos típicos


git switch -c feature/x develop
git switch develop && git merge --no-ff feature/x

git switch -c release/1.1 develop
git switch main && git merge --no-ff release/1.1
git tag -a v1.1 -m "Versión 1.1"
git switch develop && git merge --no-ff release/1.1

git switch -c hotfix/1.1.1 main

        

      

    


    

      
3. Trunk-Based Development

      
Todo el equipo integra en main (el "tronco") al menos una vez al día. Las ramas, si existen, duran horas. Lo incompleto se esconde tras feature flags.

      

      

        

          
Flujo

          
    
            
  • Commits directos al tronco o ramas de menos de 1-2 días.
    • 
            
  • CI muy rápido y obligatorio en cada integración.
    • 
            
  • El código inacabado se desactiva con feature flags, no con ramas largas.
    • 
            
  • Para publicar: se corta una rama release/* desde el tronco y solo recibe cherry-picks de arreglos.
    • 
          

          
ProsCasi sin conflictos, integración continua real, entrega muy rápida.

          
ContrasExige tests automáticos fiables, disciplina y feature flags.

        

        

          
Comandos típicos


git switch -c fix/typo main
git commit -am "Corrige typo"
git pull --rebase origin main
git push origin fix/typo
# PR pequeño, merge el mismo día

# Arreglo en una release ya cortada:
git switch release/1.x
git cherry-pick <hash-en-main>

        

      

    


    

      
4. GitLab Flow (ramas por entorno)

      
GitHub Flow más ramas que representan entornos. El código solo avanza en una dirección: main → pre-production → production.

      

      

        

          
Flujo

          
    
            
  • Las features llegan a main por PR/MR, como en GitHub Flow.
    • 
            
  • Se promueve a pre-production fusionando main en ella (despliegue a staging).
    • 
            
  • Tras validar, se fusiona a production (despliegue a producción).
    • 
            
  • Los arreglos urgentes se hacen en main primero y se promocionan igual: nunca al revés.
    • 
          

          
ProsSabes exactamente qué versión hay en cada entorno.

          
ContrasMás ramas que mantener y despliegue más lento que en GitHub Flow.

        

        

          
Comandos típicos


# Promocionar main a staging
git switch pre-production
git merge main
git push

# Tras validar, a producción
git switch production
git merge pre-production
git push

        

      

      
¿Cuál elegir? Empieza por GitHub Flow. Si necesitas entornos controlados, pasa a GitLab Flow; si mantienes varias versiones publicadas, Git Flow; y si tu CI y tus tests son excelentes, evoluciona hacia Trunk-Based.
